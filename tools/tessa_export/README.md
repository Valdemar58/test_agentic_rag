# tessa-export — экспорт голден-корпуса из СЭД Тесса

Инструмент запускается в рабочем контуре заказчика в Docker. Он берёт seed-список карточек,
раскрывает его вглубь по связям (по умолчанию до глубины 2, не более 200 документов), скачивает
файлы, сериализует карточки и собирает один архив: `files/ + cards/ + cards_raw/ + manifest.json +
links_graph.json + validation_report.md`. Ничего в Тессе не изменяется: только чтение.

## Что вы получаете от исполнителя

Папка `tessa-export-<версия>/`:

| Файл | Назначение |
|---|---|
| `tessa-export-<версия>.tar` | Docker-образ (загружается командой `docker load`) |
| `config.yaml` | Конфиг экспорта; заполнить `tessa.base_url` |
| `seed_cards.yaml` | Seed-список из 30 карточек (из ТЗ) |
| `tessa.env` | Шаблон для логина и пароля |
| `README.md` | Эта инструкция |

## Запуск (Linux-хост с Docker)

1. Загрузить образ:

   ```bash
   docker load -i tessa-export-0.1.6.tar
   ```

2. Положить рядом папки `config/` и `output/`. В `config/` — `config.yaml` и `seed_cards.yaml`.
   В `config.yaml` заполнить адрес сервера:

   ```yaml
   tessa:
     base_url: https://tessa.ваш-домен.local
   ```

   Остальные параметры менять не нужно. Пути `external.*` уже соответствуют образу.

3. Заполнить `tessa.env` (логин в формате `ДОМЕН\пользователь`, пароль). Файл никуда не передавать.

4. Проверить контейнер без доступа к Тессе (самопроверка на синтетических данных, ~10 секунд):

   ```bash
   docker run --rm -v "$PWD/output:/output" tessa-export:0.1.6 self-test --output /output/selftest
   ```

   Ожидаемый вывод заканчивается строкой `ИТОГ: сет ПРИГОДЕН`.

5. Запустить экспорт:

   ```bash
   docker run --rm --env-file tessa.env \
     -v "$PWD/config:/config:ro" -v "$PWD/output:/output" \
     tessa-export:0.1.6 run --config /config/config.yaml
   ```

   Ход работы печатается на экран, полный лог — `output/tessa_export.log`.

6. Результат в `output/`:
   - `tessa_export.zip` — архив для передачи исполнителю;
   - `export/validation_report.md` — отчёт: строка **ИТОГ: ПРИГОДЕН / НЕ ПРИГОДЕН**, проверки,
     покрытие по видам документов и рекомендации по добору;
   - `tessa_export.log` — лог.

7. Передать исполнителю `tessa_export.zip` (и `tessa_export.log`, если были ошибки).

## Отбор состава сета

Первый запуск делается с запасом (`traversal.max_docs: 400`: полное замыкание связей глубины 2).
В `output/export/documents_review.csv` (открывается в Excel, разделитель «;») одна строка на
документ: категория Тессы, номер, дата, тема, статус, из какого документа и по какой связи он
пришёл, число файлов, категории 8.2. Отметьте лишние документы в колонке «исключить» и передайте
исполнителю список ID (или целые типы карточек). Исполнитель вносит их в `exclude_rules`
конфига:

```yaml
exclude_rules:
  - reason: "первичные документы ЭДО"
    card_type_names: [PrimaryDocumentMKC, IncomingEDO]
  - reason: "отобрано вручную"
    card_ids: ["00000000-0000-0000-0000-000000000000"]
```

Повторный запуск с этим конфигом даёт воспроизводимый сет без исключённых документов:
исключённая карточка не скачивается, и её связи дальше не раскрываются. Seed-карточки правила
по типу не затрагивают (они выбраны явно); исключить seed-карточку можно только через `card_ids`
или добавив к правилу `applies_to_seed: true`.

Если полное замыкание уже скачано, повторно обращаться к Тессе не нужно: команда `filter`
применяет правила и лимиты из конфига к готовому архиву и собирает точно такой же результат
(манифест, отчёт, таблица отбора, архив), как дал бы онлайн-запуск:

```bash
docker run --rm -v "$PWD/config:/config:ro" -v "$PWD/output:/output" \
  tessa-export:0.1.6 filter --config /config/config.yaml \
  --source /output/tessa_export.zip --output /output/filtered
```

Результат в `output/filtered/`: `export/` и `tessa_export.zip`. Источником может быть и
распакованный каталог `export/`.

## Синхронизация приказов (вне ТЗ, по запросу 2026-09-18)

Отдельный режим для демонстрации: выгрузить **все приказы** и при повторных запусках
добирать только новые.

1. Найдите представление, в котором видны приказы. Перечень доступных:

```
tessa-export views --config /config/config.yaml
tessa-export views --config /config/config.yaml --alias ALIAS      # колонки и первые строки
```

2. Заполните в конфиге секцию `orders`: `view_alias`, при необходимости `parameters`
   (фильтры представления ровно в том виде, в каком их шлёт веб-клиент Тессы — их видно в
   F12 → запрос `views/get-data`), имена колонок `id_column`/`state_column`.
   `exclude_state_ids: [6]` означает, что приказы в состоянии «Зарегистрировано»
   (`$KrStates_Doc_Registered`) не выгружаются.

3. Пробный прогон без выгрузки, затем рабочий:

```
tessa-export orders --config /config/config.yaml --dry-run --limit 20
tessa-export orders --config /config/config.yaml
```

Каталог результата между запусками **не очищается**: карточки, которые уже лежат в
`output/export/`, повторно не запрашиваются, манифест и граф связей дополняются. Связанные
документы не выгружаются (`orders.max_depth: 0`) — только сами приказы. Архив по умолчанию
не собирается, добавьте `--archive`, если нужен zip.

Состояние проверяется дважды: по колонке представления (если она задана) и обязательно по полю
карточки `DocumentCommonInfo.StateID` — исключённые приказы попадают в `manifest.json`
(раздел `excluded`) с причиной, но их файлы не скачиваются.

На машине разработчика тот же цикл вместе с индексацией выполняется одной командой:

```
uv run python scripts/sync_orders.py --limit 50     # выгрузка новых приказов + инжест + глоссарий
```

## Коды завершения и что делать

| Код | Смысл | Что делать |
|---|---|---|
| 0 | Экспорт выполнен, сет пригоден | Передать `tessa_export.zip` |
| 3 | Экспорт выполнен, но валидация дала FAIL | Открыть `validation_report.md`, раздел «Проверки 8.3»; чаще всего это недоступные файлы. Архив всё равно можно передать вместе с отчётом |
| 2 | Ошибка конфигурации, учётных данных, доступа или сети | Текст ошибки на экране говорит, что исправить: `base_url`, логин/пароль, права учётной записи, доступность сервера из контейнера |
| 1 | Сбой во время работы | Прислать `output/tessa_export.log` исполнителю |

## Настройки, которые может быть полезно менять

- `traversal.max_depth`, `traversal.max_docs` — если отчёт сообщает о непройденных связях
  из-за лимитов и вы хотите включить их в сет, увеличьте значения и перезапустите.
- `files.allowed_extensions` — какие файлы скачивать (по умолчанию pdf, docx, xlsx, pptx и
  изображения; `doc` и `xls` выключены).
- `exclude_rules` — правила исключения документов (по умолчанию пусто).
- `tessa.verify_tls` — проверка TLS-сертификата сервера Тессы. По умолчанию выключена
  (`false`), потому что CA сервера в контуре нет. Чтобы включить, положите файл CA рядом
  с конфигом, смонтируйте его в контейнер и укажите путь в `tessa.ca_bundle`.
  Ошибка `CERTIFICATE_VERIFY_FAILED` при запуске означает, что в вашем `config.yaml`
  стоит `verify_tls: true` без `ca_bundle`.

Повторный запуск `run` и `filter` полностью перезаписывает `output/export/` и архив;
`orders` — наоборот, накапливает результат в том же каталоге.

## Для исполнителя: сборка образа

Из корня репозитория, с заданными `TESSA_SDK_PATH` и `CARD_SERVICE_PATH` (в `.env`):

```
pwsh tools/tessa_export/build_image.ps1 -Version 0.1.6     # Windows
tools/tessa_export/build_image.sh 0.1.6                     # Linux/macOS
```

Скрипт собирает образ (SDK Тессы и схемы сервиса карточек подключаются через build-context и
в репозиторий не попадают), сохраняет его в `dist/tessa-export-<версия>/` вместе с конфигом,
seed-списком, шаблоном `tessa.env` и этой инструкцией. Каталог `dist/` не коммитится.
