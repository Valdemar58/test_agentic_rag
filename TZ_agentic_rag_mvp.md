## 1. Контекст и цель

Разрабатывается self-hosted агентский RAG для поиска и ответов на вопросы по корпоративным документам организации (приказы, ЛНА, инструкции, положения, договоры, акты, служебные записки). Источник документов — СЭД Тесса. Целевая аудитория продакшена — ~40 сотрудников; **цель данного этапа — MVP для одного пользователя**, демонстрирующий высокое качество ответов и прозрачность работы агента.

**Определение успеха MVP:** пользователь задаёт сложный вопрос по корпусу документов; агент в видимом ему цикле находит нужные документы, проверяет их актуальность, и выдаёт корректный ответ с кликабельными цитатами до конкретного пункта конкретного приказа. Качество подтверждается метриками на голден-сете (раздел 10), а не субъективным впечатлением.

MVP закладывает архитектурный фундамент для фазы 2 (масштабирование на 2× NVIDIA DGX Spark, 10 параллельных пользователей, авторизация/ACL, гибрид LLM+SLM), но НЕ реализует её функциональность.

## 2. Ограничения окружения

| Ограничение | Значение |
|---|---|
| GPU для MVP | 1× NVIDIA RTX 3080, 12 GB VRAM |
| Контур | Полностью закрытый. Все модели, фреймворки, сервисы — локальные и бесплатные (open source). Никаких внешних API в рантайме |
| СЭД Тесса | НЕДОСТУПНА с машины разработки. Документы и карточки для разработки и метрик получаются экспорт-скриптом на SDK Тессы (раздел 8), который заказчик запускает в рабочем контуре и передаёт результат обратно |
| Карточки документов | У заказчика есть готовый FastAPI-сервис с методами получения данных карточки в виде pydantic-моделей (данные как в СЭД, без допобработки: включая статус согласования и все метаданные). В dev-среде этот сервис замещается моком, отдающим реальные экспортированные карточки в той же схеме (раздел 9) |
| ОС | Linux, Docker + docker-compose доступны |

**Бюджет VRAM (12 GB) — обязателен к соблюдению:**
- Рантайм (ответы на вопросы): LLM Qwen3-8B AWQ/GPTQ 4-bit через vLLM (~6.5 GB весов + KV-cache). Эмбеддинги и reranker в рантайме — на CPU.
- Инжест (индексация корпуса): выполняется отдельным этапом, когда LLM-сервис остановлен. dots.mocr (~3B VLM) занимает GPU монопольно. Эмбеддинги при инжесте допустимо считать на GPU после выгрузки dots.mocr.
- Одновременная загрузка LLM + dots.mocr в 12 GB запрещена архитектурно (оркестрация этапов, не надежда на везение).

## 4. Архитектура (обзор)

Два контура:

**Офлайн (инжест):** экспорт из СЭД (файлы документов + карточки в pydantic-схеме) → маршрутизатор (текстовый слой есть → нативный Docling; скан/нет слоя → Docling VLM-конвейер + dots.mocr) → DoclingDocument → чанкинг (раздел 6, FR-3) → обогащение чанков метаданными из карточки → эмбеддинги bge-m3 (dense + sparse) → Qdrant. Инжест инкрементален: повторный запуск обрабатывает только новые/изменённые файлы (по хэшу), удаляет чанки удалённых документов.

**Онлайн (запросы):** UI → агентский сервис (LlamaIndex) → MCP-сервер (поиск, карточки, связи, глоссарий) → Qdrant / сервис карточек (в dev — мок). Все шаги трейсируются в Langfuse. Диалоги и фидбэк — в PostgreSQL через SQLAlchemy.

## 5. Функциональные требования MVP

Каждое требование имеет критерии приёмки (AC). Требование считается выполненным только при прохождении всех его AC.

### FR-1. Агентский цикл

Агент работает в цикле: анализ запроса → выбор и вызов инструментов → оценка достаточности найденного → при необходимости переформулирование запроса / дополнительный поиск / переход по связям документов → синтез ответа. Решения о вызовах принимает LLM, не жёсткий конвейер.

- Бюджет: максимум 8 вызовов инструментов на запрос. По исчерпании — ответ на основе найденного с явной оговоркой о возможной неполноте.
- Самопроверка встроена в системный промпт: перед финальным ответом агент проверяет, что (а) ответ опирается только на найденные фрагменты, (б) ответ отвечает именно на вопрос пользователя, (в) использованные документы действуют (проверка поля статуса).
- Если релевантных документов не найдено — агент явно сообщает «в документах ответа нет», не сочиняет.

**AC-1.1:** на вопросе категории «мультидокументный» из голден-сета трейс в Langfuse показывает ≥2 различных поисковых запроса, сформулированных агентом.
**AC-1.2:** на вопросе категории «нет ответа» агент отвечает отказом (метрика M4, раздел 10).
**AC-1.3:** ни один запрос не приводит к >8 вызовам инструментов (проверяется тестом).

### FR-2. Инструменты агента (MCP-сервер)

Единый MCP-сервер предоставляет минимум:

1. `hybrid_search(query, filters, top_k)` — гибридный поиск в Qdrant (dense + sparse, серверный fusion) → rerank топ-20 → top_k результатов. Фильтры: тип документа, статус (по умолчанию только действующие), диапазон дат, подразделение. Возвращает чанки с метаданными и координатами (doc_id, раздел, пункт).
2. `get_document_card(doc_id)` — карточка документа. Реализуется как обёртка над FastAPI-сервисом карточек заказчика; возвращает данные в его pydantic-схеме (включая статус согласования и все метаданные), без потери полей.
3. `get_document_content(doc_id, section_id?)` — полный текст документа или раздела (для дочитывания контекста; из проиндексированного корпуса).
4. `get_related_documents(doc_id, relation_type?)` — связанные документы по связям из карточек («отменён», «изменён», «приложение к», «ссылается на»). Также обёртка над сервисом карточек.
5. `glossary_lookup(term)` — поиск по глоссарию организации (FR-5).

Обёртки над сервисом карточек проектируются так, что переключение dev-мок ↔ реальный FastAPI-сервис — это смена одного URL в конфиге, без изменений кода агента и MCP-сервера.

**AC-2.1:** каждый инструмент имеет docstring-описание, достаточное для корректного выбора его LLM (проверяется интеграционным тестом: агент вызывает правильный инструмент на 10 эталонных сценариях).
**AC-2.2:** `hybrid_search` без явного фильтра не возвращает чанки отменённых документов.
**AC-2.3:** MCP-сервер запускается автономно и покрыт юнит-тестами на каждый метод.
**AC-2.4:** контрактный тест: ответы мока и сигнатуры реального FastAPI-сервиса валидируются одними и теми же pydantic-схемами.

### FR-3. Инжест и чанкинг

- Вход инжеста — результат экспорта (раздел 8): файлы + карточки. Документ без карточки в инжест не допускается (ошибка в лог, файл пропускается).
- Маршрутизатор форматов: DOCX и PDF с текстовым слоем → нативный Docling; PDF-сканы и изображения → Docling VLM-конвейер с dots.mocr (vLLM).
- Чанкинг двухстратегийный: **основной — структурный** (по пунктам/статьям/разделам из структуры DoclingDocument, с «хлебными крошками» вида «Приказ №N от ДД.ММ.ГГГГ → Раздел 3 → п. 3.2» в тексте чанка); **фоллбэк — фиксированный** (512 токенов, overlap 64) для документов без внятной структуры. Семантический чанкинг НЕ реализуется.
- Parent-child: индексируются мелкие чанки (child, уровень пункта/абзаца), при извлечении агенту возвращается родительский контекст (parent, уровень раздела) — AutoMergingRetriever или эквивалент.
- **Метаданные каждого чанка формируются из полей карточки СЭД**, а не выводятся из текста документа. Маппинг «поле карточки → поле метаданных чанка» оформляется явной задокументированной таблицей в коде/README и согласуется с заказчиком после изучения реальных pydantic-схем. Обязательный минимум полей чанка: doc_id, тип документа (вид карточки), номер, дата, статус документа (действует/отменён/проект), статус согласования, подразделение/автор, связи (список doc_id + тип связи), уровень доступа (**acl_groups — заполняется из карточки, если поле есть, иначе заглушкой, но присутствует в схеме с первого дня** — задел под фазу 2), путь в структуре документа (раздел/пункт), хэш исходного файла, идентификатор карточки в Тессе.
- Таблицы из документов сохраняются как отдельные чанки в формате markdown-таблиц с привязкой к разделу.

**AC-3.1:** ≥95% файлов экспортированного корпуса проходят инжест без ошибок; ошибки логируются с причиной, инжест не падает целиком из-за одного файла.
**AC-3.2:** выборочная ручная проверка 10 документов: структурные чанки соответствуют реальным пунктам, хлебные крошки корректны, метаданные чанков совпадают с полями карточек.
**AC-3.3:** повторный запуск инжеста на неизменённом корпусе не создаёт дубликатов (idempotency-тест).
**AC-3.4:** скан-PDF из корпуса распознаётся через dots.mocr, текст попадает в индекс (интеграционный тест).

### FR-4. Ответы с цитатами

Каждое фактическое утверждение в ответе сопровождается ссылкой на источник: название/номер документа, дата, раздел/пункт. Ссылки кликабельны в UI (открывают текст соответствующего чанка/документа). В конце ответа — блок «Источники».

**AC-4.1:** метрики M2 и M3 (раздел 10) достигнуты.
**AC-4.2:** клик по ссылке в UI открывает текст именно того фрагмента, на который ссылается ответ (ручная проверка 10 ответов).

### FR-5. Глоссарий терминов

При инжесте из документов автоматически извлекаются разделы «Термины и определения» / «Сокращения» (по заголовкам через структуру Docling + LLM-подтверждение) в отдельную коллекцию Qdrant. Глоссарий используется: (а) агентом через `glossary_lookup`, (б) на этапе переписывания запроса — аббревиатуры в запросе пользователя расшифровываются перед поиском.

**AC-5.1:** запрос с корпоративной аббревиатурой из глоссария находит те же документы, что и запрос с полной расшифровкой (тест на ≥5 парах запросов).

### FR-6. Контекст диалога

- История текущего чата передаётся агенту (буфер последних N сообщений; при переполнении — суммаризация старых).
- Уточняющие вопросы («а для филиалов?», «а с какого числа?») переписываются в самодостаточный поисковый запрос с учётом истории до вызова поиска.
- Найденные в рамках сессии документы кэшируются: уточняющий вопрос по уже найденному документу не запускает повторный поиск с нуля, если ответ есть в уже извлечённом контексте.

**AC-6.1:** сценарный тест: вопрос → уточнение из 2–3 слов → в трейсе виден переписанный самодостаточный запрос, ответ корректен (5 эталонных сценариев).

### FR-7. UI

- Чат с выбором/созданием отдельных диалогов; история диалогов хранится в PostgreSQL (SQLAlchemy-модели, Alembic-миграции).
- Стриминг токенов ответа.
- Отображение хода работы агента в реальном времени: какие инструменты вызваны, с какими запросами, сколько найдено («Ищу в приказах по охране труда… → Найдено 4 документа → Проверяю актуальность…»). Пользователь всегда видит прогресс, а не пустое ожидание.
- Кнопки 👍/👎 на ответе; фидбэк пишется в PostgreSQL и линкуется с трейсом Langfuse (для будущих фаз; в MVP никакой логики поверх фидбэка не строится).
- Кликабельные цитаты (FR-4).

**AC-7.1:** первый видимый пользователю сигнал (шаг агента или токен) ≤ 5 секунд после отправки вопроса (метрика M6).

### FR-8. Наблюдаемость

Каждый запрос трейсируется в self-hosted Langfuse: все LLM-вызовы (промпт, ответ, токены, latency), все вызовы инструментов (аргументы, результаты), итоговый ответ. Трейс связан с диалогом и фидбэком.

**AC-8.1:** для произвольного ответа можно в Langfuse восстановить полную цепочку: запрос → переписывание → поисковые запросы → чанки → синтез.

### FR-9. Прикладная БД

Все прикладные данные (диалоги, сообщения, фидбэк, реестр проиндексированных файлов с хэшами, служебные таблицы) — в PostgreSQL (контейнер docker-compose, отдельный от Qdrant и Langfuse).

- Доступ к БД — только через SQLAlchemy ORM (модели в `src/db/models.py`). Сырые SQL-строки в коде запрещены (включая `text()`, кроме исключений, письменно согласованных в PR).
- Схема управляется Alembic: `alembic upgrade head` на чистой БД создаёт всю схему; каждое изменение схемы — новая миграция.
- БД одноразовая: удаление volume + пересоздание контейнера + миграции = рабочее состояние. Никаких ручных шагов настройки.

**AC-9.1:** тест: чистый контейнер PostgreSQL → `alembic upgrade head` → приложение работает.
**AC-9.2:** grep-проверка в CI/тестах: в `src/` отсутствуют сырые SQL-запросы.

## 6. Нефункциональные требования

- **NFR-1. Русский язык.** Все промпты, ответы, UI — на русском. Качество измеряется исключительно метриками раздела 10.
- **NFR-2. Производительность на 3080 (1 пользователь):** первый сигнал ≤5 с; полный ответ на простой вопрос ≤45 с; на сложный (мультидокументный, несколько итераций) ≤120 с.
- **NFR-3. Воспроизводимость.** Весь стенд поднимается командой `docker compose up` (+ отдельный compose/профиль для этапа инжеста). Версии всех зависимостей зафиксированы (lock-файлы, теги образов, ревизии моделей на HF).
- **NFR-4. Конфигурация** — единый файл (yaml/env): модели, пути, URL сервиса карточек (мок/реальный), параметры чанкинга, top_k, бюджет итераций. Без магических констант в коде.
- **NFR-5. Данные не покидают контур.** Никаких вызовов внешних API в рантайме. Загрузка весов моделей — разово на этапе установки, далее офлайн.
- **NFR-6. Инструментарий Python.** Управление зависимостями и окружением — только **uv** (`pyproject.toml` + `uv.lock`, коммитятся в репозиторий; requirements.txt не использовать). Вся конфигурация инструментов — в `pyproject.toml`. Линтинг и форматирование — **ruff** (lint + format, заменяет black/isort/flake8). Типизация — **mypy**: строгий режим (`disallow_untyped_defs`) для собственного кода (`src/db`, `src/mcp_server`, `src/ingest`, `src/eval`, `tools/`), послабления через `[[tool.mypy.overrides]]` (`ignore_missing_imports`) для сторонних библиотек без полных аннотаций (LlamaIndex, Docling и т.п.). Команды `uv run ruff check`, `uv run ruff format --check`, `uv run mypy`, `uv run pytest` должны проходить без ошибок — это часть Definition of Done каждого этапа, а не финальная уборка. Единая точка запуска проверок (Makefile-таргет или скрипт `check`) обязательна.

## 7. Вне рамок MVP (реализация запрещена без согласования)

Поиск в интернете; гибрид LLM+SLM с роутингом; память о пользователе и память успешных паттернов по лайкам (сбор 👍/👎 — есть, логика поверх — нет); исполнение python/bash кода агентом и песочница БД; самосоздание скиллов агентом; генерация графиков/схем в ответах; полноценная авторизация и enforcement ACL (но поле acl_groups в схеме индекса обязательно — FR-3); подключение к живой СЭД из dev-среды; семантический чанкинг; масштабирование на многопользовательский режим. Связи между документами берутся исключительно из карточек СЭД.

## 8. Экспорт голден-корпуса из СЭД (скрипт на SDK Тессы)

Отдельный поставляемый инструмент `tools/tessa_export/`. Пишется Claude Code на основе исходного кода SDK Тессы и FastAPI-сервиса карточек заказчика. **Запускается заказчиком в рабочем контуре** (СЭД из dev недоступна), результат передаётся обратно как архив. Скрипт должен быть максимально простым в запуске: один конфиг, одна команда, понятные сообщения об ошибках, поскольку исполнитель не сможет отлаживать его на месте.

### 8.0 Работа с внешним кодом SDK и сервиса карточек

Код SDK Тессы и FastAPI-сервиса карточек находится в отдельных папках вне репозитория RAG и **не копируется** в него (ни целиком, ни отдельными файлами). Правила:

- Пути к папкам передаются через конфиг/переменные окружения: `TESSA_SDK_PATH`, `CARD_SERVICE_PATH`. Claude Code читает и анализирует код по этим путям, но все изменения и новый код пишет только в репозитории RAG.
- Pydantic-схемы карточек импортируются из `CARD_SERVICE_PATH` как из внешнего пакета (добавление пути в окружение / editable-установка / указание в PYTHONPATH — способ выбрать и задокументировать в README). Схемы — единый контракт для экспорт-скрипта, мока (раздел 9), маппинга метаданных чанков (FR-3) и контрактных тестов (AC-2.4).
- Экспорт-скрипт зависит от SDK аналогично: путь к SDK — параметр его собственного конфига, поскольку в рабочем контуре заказчика путь будет другим.
- Если внешние пути недоступны (например, CI), тесты, зависящие от контракта, должны корректно скипаться с понятным сообщением, а не падать.

### 8.1 Что делает скрипт

**Вход — seed-список идентификаторов карточек**, составленный заказчиком (файл `seed_cards.yaml`: список ID, опционально комментарий к каждому). Скрипт не занимается самостоятельным отбором документов — он раскрывает заданный список вглубь. Алгоритм:

1. Для каждого ID из seed-списка: получить карточку через SDK, сериализовать её в JSON строго по pydantic-схемам FastAPI-сервиса (без потери и переименования полей), скачать **все** вложенные файлы карточки (основной документ + все вложения/приложения).
2. **Рекурсивный обход связей:** из каждой карточки извлекаются все связи и ссылки на другие карточки (все типы: «отменяет/отменён», «изменяет/изменён», «приложение к», «ссылается на», «в ответ на» и прочие, какие есть в схеме). Связанные карточки добавляются в очередь обхода и обрабатываются так же (карточка + все файлы + их связи).
3. Защита обхода: множество посещённых ID (циклы связей не приводят к зацикливанию и дублям); настраиваемая максимальная глубина рекурсии `max_depth` (по умолчанию 2 от seed-документа); предохранительный лимит общего числа документов `max_docs` (по умолчанию 200). При срабатывании лимитов обход корректно останавливается, а все непройденные связи перечисляются в отчёте — заказчик решает, поднять лимит или оставить.
4. Фильтр-исключение по ограничительным грифам/уровням доступа применяется ко ВСЕМ документам, включая добавленные рекурсивно (список исключаемых грифов — в конфиге). Исключённые документы попадают в отчёт (ID + причина, без содержимого), их связи дальше не обходятся.
5. Манифест `manifest.json`: для каждого документа — **как он попал в сет** (seed / по связи от какого документа, тип связи, глубина), вид карточки, статус, формат файлов, наличие текстового слоя, размеры. Отдельно `links_graph.json` — полный граф связей внутри сета (список рёбер: from_id, to_id, relation_type); он же затем используется моком сервиса карточек и инжестом.
6. Отчёт покрытия против рекомендаций 8.2, валидация 8.3, упаковка результата в один архив: `files/` + `cards/` + `manifest.json` + `links_graph.json` + `validation_report.md`.

### 8.2 Рекомендуемый состав корпуса (проверяется отчётом, а не отбором)

Состав сета определяется seed-списком заказчика, поэтому таблица ниже — не критерий отбора, а **чек-лист качества**: скрипт считает фактическое покрытие (с учётом рекурсивно добавленных документов) и в отчёте показывает дефициты, чтобы заказчик при необходимости дополнил seed-список и перезапустил экспорт. Ориентир — ~70 документов:

| Вид документа | Кол-во | Желательные подусловия |
|---|---|---|
| Приказы | 20 | из них ≥5 отменённых; ≥5 состоящих в связке «отменяет/изменяет» с другим приказом сета; ≥3 с разделом «Термины и определения» |
| Положения / ЛНА | 10 | ≥2 с разделом терминов |
| Инструкции | 10 | ≥3 со списками/таблицами |
| Договоры | 10 | ≥3 с допсоглашениями или приложениями |
| Акты | 5 | — |
| Служебные записки | 10 | ≥3 со ссылками на другие документы сета |
| Прочие виды | 5 | — |

Сквозные ориентиры: ≥60% файлов — цифровые DOCX/PDF с текстовым слоем; **≥15% — сканы** (проверка ветки dots.mocr); ≥10 документов с таблицами; распределение по датам не уже 3 лет (для вопросов на актуальность). Дефицит по любому пункту — не блокер экспорта, но фиксируется в `validation_report.md` как предупреждение с рекомендацией по добору.

### 8.3 Валидация качества голден-корпуса (автоматическая, в скрипте)

- Отчёт покрытия против чек-листа 8.2 (фактические цифры + список дефицитов).
- Каждый файл скачан, ненулевого размера, открывается соответствующей библиотекой (smoke-парсинг первой страницы).
- Каждая карточка проходит валидацию pydantic-схемой; список полей с пустыми значениями — в отчёт.
- **Полнота обхода связей:** висячих связей внутри пройденной глубины нет (обеспечивается самим рекурсивным обходом); все связи, не пройденные из-за `max_depth`/`max_docs`/грифов, явно перечислены с указанием причины.
- Дедупликация по идентификатору карточки и по хэшу файла (один документ, достижимый несколькими путями обхода, присутствует в сете ровно один раз; все пути входа отражены в манифесте).
- Отсутствие документов с исключёнными грифами (повторная проверка после обхода).

**AC-EXP.1:** скрипт с мок-заглушкой SDK проходит e2e-тест в dev на фикстурах: seed-список → рекурсивный обход (фикстуры содержат цикл связей и связь глубже max_depth — проверка защиты от циклов и корректной остановки) → валидация → архив.
**AC-EXP.2:** `validation_report.md` однозначно отвечает: пригоден ли сет (все проверки 8.3 — pass/fail со списком проблем и предупреждений покрытия).

## 9. Мок сервиса карточек в dev-среде

- Мок — это HTTP-сервис (FastAPI), реализующий **те же эндпоинты и те же pydantic-схемы**, что и реальный сервис карточек заказчика, но читающий данные из `cards/` экспортированного архива. Ручное составление карточек JSON вручную запрещено — источником правды являются только сериализованные скриптом реальные карточки.
- Переключение мок ↔ реальный сервис — один URL в конфиге (NFR-4), подтверждается контрактным тестом AC-2.4.
- До получения реального экспорта разработка ведётся на фикстурах, **сгенерированных программно из pydantic-схем** (валидные по схеме синтетические карточки + синтетические документы), с обязательной пометкой в README и в отчётах метрик: «данные синтетические». Финальные метрики M1–M8 снимаются только на реальном экспортированном корпусе.

## 10. Метрики качества и приёмка

### 10.1 Голден-сет вопросов

Файл `eval/golden_set.yaml` (человекочитаемый, легко редактируемый): список вопросов с полями `id`, `category`, `question`, `expected_answer` (эталонный ответ или ключевые факты), `expected_doc_ids` (документы, обязанные быть в источниках), `notes`. Минимум 50 вопросов, составляются по экспортированному корпусу (раздел 8). Категории (обязательное поле):

- `simple` — ответ в одном документе (≥15 вопросов);
- `multi_doc` — полный ответ требует ≥2 документов (≥10);
- `duplicated` — ответ присутствует в нескольких документах (≥5);
- `no_answer` — ответа в корпусе нет (≥8);
- `contradiction` — документы противоречат (отменённый vs действующий приказ, разные даты) (≥7);
- `clarification` — двухходовый сценарий с уточняющим вопросом (≥5).

Вопросы готовятся совместно: Claude Code предлагает черновик по корпусу, заказчик валидирует. Формат позволяет тривиально добавлять новые документы и вопросы.

### 10.2 Eval-harness

CLI `python -m eval.run` прогоняет весь голден-сет через агента и выдаёт отчёт (markdown + json) с метриками по категориям и в целом, плюс diff с прошлым прогоном. Проверки:

- попадание `expected_doc_ids` в источники ответа — детерминированно;
- фактическая корректность и groundedness — LLM-as-judge на локальной модели (той же Qwen3-8B с отдельным судейским промптом) + обязательная ручная валидация судьи на первых 20 вопросах (согласие судьи с человеком ≥80%, иначе судейский промпт дорабатывается);
- валидность цитат — детерминированно (каждая ссылка резолвится в существующий чанк).

### 10.3 Целевые значения (Definition of Done по качеству)

| ID | Метрика | Как считается | Цель MVP |
|---|---|---|---|
| M1 | Retrieval hit rate | Доля вопросов (simple + multi_doc + duplicated), где все expected_doc_ids присутствуют в источниках финального ответа | ≥85% simple; ≥70% multi_doc |
| M2 | Citation coverage | Доля фактических утверждений ответа, снабжённых ссылкой на источник (LLM-judge) | ≥90% |
| M3 | Citation validity | Доля ссылок, резолвящихся в реальный чанк, поддерживающий утверждение | 100% резолвятся; ≥90% поддерживают (judge) |
| M4 | Отказ при отсутствии ответа | Доля `no_answer`-вопросов с корректным явным отказом без выдумывания | ≥80% |
| M5 | Обработка противоречий | Доля `contradiction`-вопросов, где агент опёрся на действующий документ и/или явно назвал противоречие | ≥70% |
| M6 | Latency первого сигнала | p95 по прогону голден-сета | ≤5 с |
| M7 | Answer correctness | Соответствие ответа expected_answer (judge, шкала 1–5), среднее по simple | ≥4.0 |
| M8 | Инжест | Доля файлов корпуса, успешно проиндексированных | ≥95% |

Приёмка MVP = все FR-AC и AC-EXP выполнены + все M1–M8 достигнуты на голден-сете по реальному экспортированному корпусу + отчёт eval-harness приложен.

## 11. Этапы работ (рекомендуемый порядок)

1. **Изучение входных проектов:** анализ кода SDK Тессы и FastAPI-сервиса карточек по внешним путям (`TESSA_SDK_PATH`, `CARD_SERVICE_PATH`, раздел 8.0); настройка импорта pydantic-схем как общего контракта; черновик маппинга «поля карточки → метаданные чанка» на согласование.
2. **Экспорт-скрипт (раздел 8) — как можно раньше:** он исполняется заказчиком в рабочем контуре, у него самый длинный внешний цикл (передача, запуск, возврат архива). AC-EXP.*. Параллельно с ожиданием результата — следующие этапы на синтетических фикстурах.
3. **Каркас:** docker-compose (Qdrant, vLLM+Qwen3-8B, PostgreSQL, Langfuse, UI), Alembic-инициализация, конфиг, скелет репозитория. Smoke-тест: LLM отвечает, Qdrant и PostgreSQL доступны, миграции применяются.
4. **Инжест:** Docling-конвейер + маршрутизатор + dots.mocr, чанкинг, метаданные из карточек, запись в Qdrant. AC-3.*.
5. **Мок сервиса карточек + MCP-сервер:** пять инструментов, контрактные тесты. AC-2.*.
6. **Агент:** LlamaIndex-агент, системный промпт, цикл, самопроверка, переписывание запросов, контекст диалога. AC-1.*, AC-6.*.
7. **UI и цитаты:** чат, стриминг, шаги агента, кликабельные источники, фидбэк в PostgreSQL. AC-4.*, AC-7.*, AC-9.*.
8. **Глоссарий:** извлечение и подключение. AC-5.*.
9. **Eval:** переиндексация на реальном экспорте, голден-сет вопросов (черновик → валидация заказчиком), harness, прогон, итерации промптов/параметров до достижения M1–M8.
10. **Финализация:** README (установка, запуск инжеста и рантайма, снятие метрик), отчёт о метриках, список известных ограничений.

После каждого этапа — работающее состояние (можно продемонстрировать), коммиты атомарные.

## 13. Открытые вопросы к заказчику (задать до начала соответствующих этапов)

1. Сообщить пути к папкам с кодом SDK Тессы и FastAPI-сервиса карточек для `TESSA_SDK_PATH` и `CARD_SERVICE_PATH` (этап 1; код в репозиторий RAG не копируется — раздел 8.0).

3. Запустить экспорт-скрипт в рабочем контуре и передать архив (после этапа 2).
4. Согласовать маппинг «поля карточки → метаданные чанка» (этап 1–4).
5. Валидировать черновик голден-сета вопросов (этап 9).
6. Выбор UI (Open WebUI vs Chainlit) — исполнитель предлагает вариант с обоснованием, заказчик утверждает (этап 3).
