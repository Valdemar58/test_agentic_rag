# Запуск на test-машине: от пустой машины до вопросов по приказам

Сценарий: на test-машине есть доступ к Тессе, оттуда выгружаются все действующие приказы,
индексируются и становятся доступны для вопросов в UI. Повторный запуск добирает только новое.

Общий путь стенда описан в `README.md`; здесь — конкретная последовательность для этой задачи.

## 0. Что должно быть на машине

| Что | Зачем | Проверка |
|---|---|---|
| GPU NVIDIA ≥ 12 ГиБ, драйвер ≥ 575 | LLM и OCR-модель | `nvidia-smi` |
| Docker + docker compose + NVIDIA Container Toolkit | стенд | `docker run --rm --gpus all nvidia/cuda:12.9.0-base-ubuntu22.04 nvidia-smi` |
| Оперативная память ≥ 16 ГиБ (для Docker Desktop — столько же в VM) | контейнеры + reranker на CPU | — |
| Диск ≥ 60 ГиБ | веса моделей ~16 ГиБ, образы, корпус, индекс | — |
| Python 3.13 и [uv](https://docs.astral.sh/uv/) | инжест, выгрузка и скрипты запускаются на хосте, не в контейнере | `uv --version` |
| Сеть до сервера Тессы | выгрузка документов | `curl -k https://<адрес Тессы>/` |
| Учётная запись Тессы с правами на чтение приказов и файлов | выгрузка | шаг 4 |
| SDK Тессы (`tessa_client`) | выгрузка документов из Тессы | пакет из внутреннего индекса или каталог репозитория с `src/tessa_client` |
| Проект сервиса карточек (`robot_skills`) | **только** для мока сервиса карточек и для сохранения карточек в его схеме при выгрузке; агенту, MCP-серверу, UI и инжесту он не нужен. Не требует установки — достаточно каталога проекта | каталог с `src/robot_skills`, либо вместо мока поднять настоящий сервис карточек и указать `CARD_SERVICE_URL` |
| Интернет или зеркало PyPI и Hugging Face | `uv sync`, сборка образа, веса моделей | шаги 1–2 |

Если интернета на машине нет, см. «Закрытый контур» в конце.

## 1. Репозиторий и окружение

```
git clone <репозиторий> agentic_rag
cd agentic_rag
uv sync
uv run python scripts/check.py      # ruff + mypy + тесты: убеждаемся, что окружение собралось
```

## 2. Веса моделей

```
uv run python scripts/download_models.py          # ~16 ГиБ: Qwen3-8B AWQ, dots.mocr, bge-m3, reranker, Docling
uv run python scripts/download_models.py --check  # что уже на месте
```

Ревизии зафиксированы в `configs/app.yaml`, повторный запуск ничего не перекачивает. Рантайм
работает офлайн (`HF_HUB_OFFLINE=1`).

## 3. Файл `.env`

```
cp .env.example .env
```

Заполнить обязательно:

```
TESSA_SDK_PATH=/путь/к/tessa_sdk            # каталог с src/tessa_client
CARD_SERVICE_PATH=/путь/к/robot_skills      # каталог с src/robot_skills
CORPUS_DIR=./data/orders                    # корпус приказов: его отдаёт мок сервиса карточек
UI_USERNAME=…
UI_PASSWORD=…
CHAINLIT_AUTH_SECRET=…                      # uv run chainlit create-secret
```

**Про два внешних проекта.** `TESSA_SDK_PATH` и `CARD_SERVICE_PATH` — это **каталоги**, а не
установленные пакеты: подключается подкаталог `src` каждого. Ставить их в окружение не нужно;
`git clone` рядом с репозиторием достаточно. Эти же переменные видит выгрузка — путь можно задать
либо здесь, либо в секции `external` её конфига (конфиг важнее, если путь в нём рабочий).

Если `tessa_client` приезжает колесом из внутреннего devpi, `TESSA_SDK_PATH` можно оставить
пустым — пакет найдётся в окружении. Ставить его нужно **после** `uv sync`: тот удаляет из
окружения всё, чего нет в `uv.lock`.

```
uv pip install --index-url https://<devpi>/root/<индекс>/+simple/ tessa-client
uv run python -c "import tessa_client; print('ок')"
```

`robot_skills` нужен только двум вещам: моку сервиса карточек и шагу выгрузки, который сохраняет
карточки в схеме этого сервиса. Варианты:

- указать `CARD_SERVICE_PATH` на каталог проекта (ничего не устанавливая);
- либо не поднимать мок вообще: запустить настоящий сервис карточек и указать на него
  `CARD_SERVICE_URL` (и `CARD_SERVICE_URL_DOCKER` для контейнеров) — тогда агент берёт карточки
  из него. Выгрузке каталог всё равно понадобится.

В контейнерах (`mock-card-service`) внешний код монтируется томами из тех же переменных;
`mcp-server`, `agent-ui` и инжест его не используют.

Учётные данные Тессы — там же, в `.env`, рядом с остальными:

```
TESSA_USERNAME=ДОМЕН\пользователь
TESSA_PASSWORD=…
```

Если удобнее держать их только в памяти сессии, переменная окружения перекрывает файл:

```powershell
$env:TESSA_USERNAME = 'ДОМЕН\пользователь'; $env:TESSA_PASSWORD = '…'   # PowerShell
```
```bash
export TESSA_USERNAME='ДОМЕН\пользователь' TESSA_PASSWORD='…'          # bash
```

## 4. Конфиг выгрузки

```
cp tools/tessa_export/config.example.yaml tools/tessa_export/config.yaml
```

Поправить в нём:

```yaml
tessa:
  base_url: https://<адрес Тессы>
# секцию external можно убрать целиком, если пути заданы в .env или пакеты стоят из devpi;
# оставите — там пути контейнера из примера, замените на реальные
orders:
  view_alias: OrderMKCDocuments_09062025     # представление приказов
  include_state_ids: [6]                     # только действующие («Зарегистрировано»)
```

Проверка связи и представления (карточки ещё не скачиваются):

```
uv run tessa-export views --config tools/tessa_export/config.yaml --alias OrderMKCDocuments_09062025
uv run tessa-export orders --config tools/tessa_export/config.yaml --output data/orders --dry-run --limit 20
```

Первая команда покажет колонки представления. Если в нём нет колонки `StateID`, поставьте
`state_column: null` — состояние всё равно проверяется по карточке. Вторая покажет, сколько
приказов отобрано и сколько отсеяно по состоянию, ничего не выгружая.

## 5. Стенд

```
uv run python scripts/stack.py up base      # Qdrant и PostgreSQL
uv run alembic upgrade head                 # схема прикладной БД (реестр инжеста, диалоги UI)
```

Образ приложения (MCP-сервер, UI, мок карточек) собирается сам при первом подъёме профиля
`runtime` — это несколько минут и требует сети.

## 6. Выгрузка приказов и индексация

```
uv run python scripts/sync_orders.py --limit 50    # пробный объём
uv run python scripts/sync_orders.py               # все приказы
```

Что происходит: выгружаются карточки и файлы приказов в `data/orders/` → инжест разбирает новые
файлы (сканы — через OCR-модель, для этого скрипт сам поднимает профиль `ingest` и потом
возвращает `runtime`) → считаются эмбеддинги → пишется индекс Qdrant → собирается глоссарий.

Время: первый прогон — десятки минут на сотни документов (узкое место — OCR сканов).
Повторный прогон: уже выгруженные приказы не запрашиваются, уже разобранные файлы не
разбираются, поэтому он быстрый.

Полезные флаги: `--dry-run` (только план), `--export-only` / `--ingest-only` (один шаг),
`--limit N`.

## 7. Вопросы

Профиль `runtime` синхронизация поднимает сама в конце прогона. Если стенд перезапускали:

```
uv run python scripts/stack.py up runtime --wait    # Qwen3-8B, MCP-сервер, мок карточек, UI
```

UI — http://localhost:8080, вход по `UI_USERNAME` / `UI_PASSWORD`. Проверка стенда перед
демонстрацией:

```
uv run python scripts/smoke.py    # база и миграции, Qdrant, ответ LLM по-русски, вызов инструмента
```

Вопрос без UI, одной командой: `uv run python -m agent "Какие приказы об охране труда действуют?"`

## 8. Повторный прогон (регулярное обновление)

```
uv run python scripts/sync_orders.py
```

Больше ничего делать не нужно: стенд остаётся поднятым, UI подхватывает обновлённый индекс.
Если стенд был остановлен — сначала `stack.py up base`, после прогона `stack.py up runtime --wait`.

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| `ОШИБКА КОНФИГУРАЦИИ: не заданы учётные данные Тессы` | нет `TESSA_USERNAME` / `TESSA_PASSWORD` ни в окружении, ни в `.env` (ищется в каталоге запуска и рядом с конфигом) |
| `SDK Тессы не найден: … и пакет tessa_client не установлен` | ни путь в конфиге, ни установленный пакет; задайте `external.*` или поставьте пакеты из внутреннего индекса (шаг 3). После `uv sync` установку из devpi нужно повторить |
| `ОШИБКА СЕТИ` при выгрузке | неверный `tessa.base_url` или сервер недоступен; при ошибке сертификата — `tessa.verify_tls: false` (по умолчанию) или свой CA в `tessa.ca_bundle` |
| `в представлении «…» нет колонок …` | имена колонок в конфиге не совпали с представлением; посмотреть `tessa-export views --alias …` |
| `не задан orders.view_alias` | не заполнена секция `orders` в конфиге выгрузки |
| `СМЕНА КОРПУСА: …` при инжесте | индекс собран из другого каталога; это защита от стирания. Либо укажите прежний каталог, либо повторите с `--switch-corpus`, согласившись удалить из индекса всё, чего нет в новом корпусе |
| `ИТОГ: сет НЕ ПРИГОДЕН` после выгрузки | проверки §8.3 оценивают состав голден-корпуса (виды документов, доля сканов, открылись ли все файлы) — к индексации архив пригоден, инжест продолжается. Что именно не сошлось — в `validation_report.md` |
| Вопрос в UI висит «Модель ещё загружается» | vLLM поднимает модель после старта (до 10 минут на холодную) |
| Инжест жалуется на GPU | одновременно подняты профили `runtime` и `ingest`; они взаимоисключены, `stack.py up … --switch` переключает |
| Логи | выгрузка — `data/orders/tessa_export.log`; инжест — `data/work/reports/`; контейнеры — `uv run python scripts/stack.py compose -- logs -f <сервис>` |

## Закрытый контур (нет интернета)

Понадобится подготовить на машине с сетью и перенести:

1. `models/` целиком (~16 ГиБ) — веса читаются офлайн, скачивать на test-машине не нужно.
2. Образ приложения: `docker save agentic-rag-app:dev` → `docker load` на test-машине; так же
   образы `vllm/vllm-openai`, `qdrant/qdrant`, `postgres`.
3. Зависимости Python: `uv sync` требует PyPI. Либо зеркало (devpi, `UV_INDEX_URL`), либо перенос
   кэша uv.
4. SDK Тессы и схемы сервиса карточек — каталогами репозиториев или пакетами из внутреннего индекса.

Выгрузку можно выполнять и отдельным Docker-образом экспорт-скрипта, не разворачивая весь
репозиторий, — инструкция в `tools/tessa_export/README.md`.
