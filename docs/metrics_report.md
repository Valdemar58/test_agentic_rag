## Разброс между прогонами

Одна и та же конфигурация даёт **±10–15 п.п.** в категориях по 6–10 вопросов: один вопрос там
стоит 10–17 п.п. Отсюда два следствия:

- значение метрики принимается по медиане трёх прогонов, а не по лучшему прогону;
- разница между конфигурациями меньше 10 п.п. в таких категориях ничего не доказывает.

Надёжно это лечится только размером сета: чтобы одна ошибка стоила ≤ 5 п.п., нужно ≥ 20 вопросов
в категории, то есть сет примерно вдвое больше нынешнего.

## Что не достигнуто и почему

### M1-multi_doc — 60 % при цели 70 %

Вопрос требует собрать факты из нескольких документов. Разбор прогонов показал, что решает не
качество поиска, а то, на сколько частей разбит вопрос перед поиском:

- при агрессивном делении вопроса моделью метрика поднималась до 90 %, но вопросы об одном факте
  начинали тратить бюджет на лишние поиски, и M7 падала до 4,25;
- при осторожном делении наоборот: M7 держится на 4,5–4,7, а multi_doc проваливается.

Раннер уже выполняет отдельные поиски по частям вопроса до цикла инструментов
(`agent.separate_searches`), это и подняло метрику с 50 до 60–90 % в разных прогонах. Дальше
упирается в бюджет 8 вызовов инструментов, зафиксированный FR-1.

Варианты (решение за заказчиком):
1. Разбирать части вопроса кодом, а не моделью (детерминированное правило по союзам, перечислениям
   и вопросительным словам) — не тратит вызовы инструментов и не зависит от прогона.
2. Увеличить бюджет вызовов для вопросов, где найдено меньше ожидаемого — отступление от FR-1.
3. Расширить сет до ~20 вопросов в категории и перемерить: нынешние 60 % и целевые 70 % различаются
   на один вопрос из десяти.

### M3-support — 79 % при цели 90 %

Ссылки резолвятся все (M3-resolve = 100 %), но примерно каждая пятая, по мнению судьи, не
подтверждает утверждение, рядом с которым стоит. Ручная выборка дала два повторяющихся образца:

- ссылка на карточку документа стоит рядом с утверждением о тексте документа (и наоборот);
- ссылка стоит рядом с выводом, который получен из фрагмента, но дословно в нём не написан.

Лечится детерминированной проверкой каждой ссылки — тем же приёмом «модель называет, код
применяет», который уже работает на проверке черновика: отдельный вызов называет ссылки, не
подтверждающие своё утверждение, а код их снимает или заменяет. Это отдельная задача, в MVP не
входила.

## Как воспроизвести

```
uv run python scripts/stack.py up runtime
uv run python scripts/run_ingest.py run --corpus data/<архив> --restore-runtime
uv run python -m eval.run --tag <метка>
```

Отчёт прогона — `eval/reports/<метка>.md` (таблица метрик, разбор по каждому вопросу, diff с
предыдущим прогоном) и `<метка>.json` для сравнения.
