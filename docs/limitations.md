# Известные ограничения MVP и задел под следующую фазу

Дата: 2026-09-18. Дополняет `docs/metrics_report.md` (что измерено) и `PLAN.md` (как делалось).

## Сознательно не реализовано (раздел 7 ТЗ)

Это не недоработки, а граница MVP. Реализация любого пункта — отдельное согласование.

| Пункт | Как обстоит сейчас |
|---|---|
| Поиск в интернете | Рантайм полностью офлайн: `HF_HUB_OFFLINE=1`, телеметрия выключена, внешних вызовов нет |
| Гибрид LLM + SLM | Одна модель на все роли (Qwen3-8B AWQ), режим размышлений включается по ролям |
| Память о пользователе, логика поверх 👍/👎 | Оценки пишутся в БД и в Langfuse, но ни на что не влияют |
| Исполнение кода агентом, самосоздание скиллов | Инструментов ровно пять, список фиксирован MCP-сервером |
| Генерация графиков | Ответ — только текст со ссылками |
| Авторизация и enforcement ACL | Поле `acl_groups` есть в схеме индекса и всегда пустое; фильтрации по правам нет — кто вошёл в UI, видит весь проиндексированный корпус |
| Подключение к живой СЭД из рантайма dev | Агент ходит в мок сервиса карточек; живая Тесса — только у экспорт-скрипта (и у режима синхронизации приказов, добавленного по запросу заказчика) |
| Семантический чанкинг | Чанкер структурный: по заголовкам, нумерации пунктов и приложениям |
| Многопользовательский режим | Один пользователь: вход по паролю в dev, OIDC в контуре заказчика; диалоги не разделены по пользователям |

## Измеренные ограничения качества

- **M1-multi_doc 60 % при цели 70 %** и **M3-support 79 % при цели 90 %** — разбор и варианты
  решения в `docs/metrics_report.md`.
- **Разброс метрик ±10–15 п.п.** между прогонами одной конфигурации: в категориях по 6–10 вопросов
  один вопрос стоит 10–17 п.п. Значения принимаются по медиане трёх прогонов.
- **Голден-сет не валидирован заказчиком** (вопрос О7): вопросы, эталоны и ожидаемые документы
  составлены исполнителем по корпусу и проверены поиском по индексу, но не подтверждены носителем
  предметной области. До валидации метрики — самооценка.

## Ограничения обработки документов

- **M8 = 99,1 %**: три файла из 322 не разобраны — xlsx, который не открывает Docling, и два
  приложения без текстового слоя после OCR. Основной текст всех документов в индексе.
- Форматы `doc` и `xls` не обрабатываются (решение заказчика): нужен LibreOffice в образе.
- Качество распознавания сканов зависит от dots.mocr; отдельно по страницам не измерялось —
  проверено, что маршрут работает и текст извлекается (AC-3.4).
- В индекс идёт только последняя версия файла (допущение N1): история версий не ищется.
- Связи между документами берутся только из карточек СЭД; тип входящей связи восстанавливается
  через карточку-источник, поэтому у части входящих связей типа нет.
- Карточка отдаётся агенту не целиком, а списком секций из конфига (N21): полная карточка до
  575 КБ не помещается в контекст 16 384 токена.
- Глоссарий собирается по всем документам, включая отменённые (N23): из 229 записей 87 — из
  отменённых документов, статус источника виден агенту и в ответе.

## Ограничения стенда

- **Один индекс на стенд.** Прогон инжеста по другому каталогу корпуса удаляет из индекса всё,
  чего в новом корпусе нет; такой прогон требует явного `--switch-corpus`. Держать два корпуса
  одновременно (например, голден-корпус и все приказы) нельзя.
- **Профили `runtime` и `ingest` взаимоисключены**: dots.mocr и Qwen не помещаются в 12 ГиБ вместе.
  Пока идёт инжест сканов, агент недоступен.
- **Reranker на CPU**: 1,5 с на запрос при int8 и 20 кандидатах на машине разработки. На машине
  приёмки CPU другой — перемерить.
- **Контекст 16 384 токена** — узкое место на договорах с приложениями: свидетельства урезаются под
  остаток контекста, при отказе vLLM повторяется с меньшим объёмом. Ответ при этом опирается на
  меньший объём текста, чем нашёл поиск.
- Langfuse — отдельный профиль, по умолчанию выключен (память VM Docker Desktop 16 ГиБ).

## Задел под следующую фазу

Что уже готово к расширению:

- **Права доступа**: `acl_groups` есть в схеме индекса и заполняется пустым списком — фильтр по
  группам пользователя добавляется без переиндексации схемы.
- **Многопользовательский режим**: диалоги, сообщения, элементы и оценки уже лежат в своей схеме
  PostgreSQL через data layer; нужен идентификатор пользователя в ключах и фильтрах.
- **Реальный сервис карточек**: переключение мок ↔ реальный сервис — одна переменная окружения,
  контракт схем проверяется тестом.
- **Обратная связь**: 👍/👎 с `trace_id` копятся в БД и в Langfuse — готовая выборка для настройки.
- **Синхронизация из Тессы**: режим `orders` — первый шаг к регулярной выгрузке; тот же механизм
  (перечень из представления + накопительный экспорт) распространяется на другие виды документов
  сменой настроек, без нового кода.

Первоочередные доработки по итогам замера:

1. Детерминированная проверка каждой ссылки (M3-support).
2. Разбор частей многочастного вопроса кодом (M1-multi_doc).
3. Расширение голден-сета до ~20 вопросов в категории, чтобы метрики перестали скакать.
4. Валидация голден-сета носителем предметной области (О7).
