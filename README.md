# Агентский RAG по документам СЭД Тесса — MVP

Реализация по `TZ_agentic_rag_mvp.md`. Ход работ — в `PLAN.md`, правила — в `CLAUDE.md`.

> Статус: этапы 1–9 завершены, идёт этап 10 (финализация). Реальный корпус получен экспорт-скриптом
> (этап 2), проиндексирован (этап 4) и лежит вне репозитория; в репозитории и в тестах — только
> синтетический корпус (`scripts/make_synthetic_corpus.py`), **данные синтетические**. Метрики M1–M8
> снимаются только на реальном корпусе; последний замер — `docs/metrics_report.md`.

## Требования

- Python 3.13, [uv](https://docs.astral.sh/uv/)
- Docker + docker compose с NVIDIA Container Toolkit (драйвер ≥ 575 для образа vLLM CUDA 12.9)
- GPU: целевая — RTX 3080 12 ГиБ; бюджет VRAM 12 ГиБ соблюдается на любой карте
  (`gpu` в `configs/app.yaml`, доля памяти считается скриптом стенда)
- Память VM Docker Desktop: 16 ГиБ (лимиты контейнеров в `docker-compose.yml`)

## Быстрый старт

```
uv sync
cp .env.example .env               # TESSA_SDK_PATH, CARD_SERVICE_PATH, при необходимости порты
uv run python scripts/check.py     # ruff + format + mypy + pytest (или make check)
```

## Стенд (этап 3)

```
uv run python scripts/download_models.py        # веса по pinned-ревизиям в models/ (разово, ~16 ГиБ)
uv run python scripts/stack.py up runtime        # qdrant, postgres-app, vllm-qwen (Qwen3-8B AWQ)
uv run alembic upgrade head                      # схема прикладной БД
uv run python scripts/smoke.py                   # БД и миграции, Qdrant, LLM по-русски, tool calling
uv run python scripts/stack.py up ingest --switch   # dots.mocr вместо Qwen (профили взаимоисключены)
uv run python scripts/stack.py up runtime --observability   # + Langfuse (http://localhost:3000)
uv run python scripts/stack.py down
```

- `stack.py` вычисляет `--gpu-memory-utilization` из бюджета в гибибайтах и фактического объёма карты,
  поэтому vLLM получает одинаковый объём на RTX 3080 и на карте разработки.
- Профили `runtime` (Qwen3-8B) и `ingest` (dots.mocr) нельзя поднять одновременно: `up` второго
  завершается ошибкой, `--switch` останавливает первый.
- Все параметры — в `configs/app.yaml`; секреты, URL и порты — в `.env` (см. `.env.example`).
  Порты инфраструктуры публикуются только на 127.0.0.1; если 5432 занят, задайте `APP_DB_PORT`.
- Рантайм офлайн: `HF_HUB_OFFLINE=1`, телеметрия vLLM, Qdrant и Langfuse выключена.

## Экспорт корпуса из Тессы (этап 2)

Корпус собирается отдельным инструментом в контуре заказчика: он ходит в Тессу по SDK, выгружает
карточки, файлы, граф связей и отчёт о пригодности сета. В репозиторий результат не попадает.

```
tessa-export run --config config.yaml       # seed-список + обход связей (§8 ТЗ) → tessa_export.zip
tessa-export self-test                      # проверка контейнера на синтетических данных
```

Инструкция для заказчика (docker load / docker run, настройки, коды выхода) —
`tools/tessa_export/README.md`; шаблон конфига — `tools/tessa_export/config.example.yaml`.
Учётные данные только из окружения: `TESSA_USERNAME`, `TESSA_PASSWORD`.

Результат распаковывается в `data/<архив>/` (каталог `export/` с `cards`, `cards_raw`, `files`,
`manifest.json`, `links_graph.json`) и подаётся инжесту как `--corpus`.

### Синхронизация приказов (вне ТЗ, по запросу заказчика)

Отдельный режим для демонстрации: выгрузить все приказы Тессы и при повторных прогонах добирать
только новые. Перечень берётся из представления Тессы (в API нет запроса «все карточки вида X»),
выгружаются только приказы в состоянии «Зарегистрировано» (`$KrStates_Doc_Registered`, 6) — то есть
действующие; проекты и несогласованные документы в корпус не попадают.

```
tessa-export views --config config.yaml                 # какие представления доступны
tessa-export views --config config.yaml --alias ALIAS   # колонки, параметры и первые строки
tessa-export orders --config config.yaml --dry-run      # план: сколько новых, сколько отсеяно
uv run python scripts/sync_orders.py --limit 50         # выгрузка новых + инжест + глоссарий одной командой
```

Каталог (`paths.orders_dir`, по умолчанию `data/orders`) накапливается между прогонами: карточки,
которые уже выгружены, повторно не запрашиваются, манифест и граф связей дополняются. Настройки —
секция `orders` в конфиге экспорта.

Индекс один на стенд, поэтому прогон инжеста по другому каталогу корпуса удалил бы из него всё
чужое. Такой прогон останавливается предупреждением и требует явного `--switch-corpus`. Практическое
следствие: первая синхронизация приказов в отдельный каталог вытеснит из индекса голден-корпус, и
метрики придётся снимать заново после возврата на прежний каталог. Чтобы приказы дополняли текущий
корпус, а не заменяли его, укажите `--corpus` на каталог голден-корпуса — выгрузка в него дописывает
новые документы, ничего не удаляя.

## Инжест (этап 4)

```
uv run python scripts/run_ingest.py inspect --corpus data/<архив>   # состав, роли файлов, маршруты разбора
uv run python scripts/run_ingest.py run --corpus data/<архив>       # разбор (dots.mocr на GPU) → эмбеддинги → Qdrant
uv run python scripts/run_ingest.py glossary                        # глоссарий по индексу (нужен профиль runtime)
```

Инжест сам переключает GPU-профили: поднимает `vllm-dots` на время разбора сканов, затем считает
эмбеддинги bge-m3 на освободившейся карте. Повторный запуск обрабатывает только новые и изменённые
файлы (реестр в PostgreSQL). Отчёт — `data/work/reports/`. Разобранные документы кэшируются в
`data/work/parsed`, поэтому `--force` после правок чанкера переиндексирует корпус за минуты без OCR.
Чанкер структурный: разделы и пункты по заголовкам и нумерации, приложения внутри документа
(«Приложение № N» с названием) — отдельные разделы, перечни в приложениях — одним чанком, строки
оглавления пропускаются, перечень после абзаца с двоеточием («…в следующем диапазоне:») остаётся в чанке
своего пункта.

Глоссарий (FR-5) собирается отдельным шагом по уже построенному индексу — `run_ingest.py glossary` или
автоматически в конце `run`, если профиль `runtime` поднят (`--restore-runtime`): разделы «Термины и
определения» и «Сокращения» (заголовки из `glossary.headings`) дают строки «термин — определение»,
Qwen подтверждает раздел и называет строки, которые терминами не являются, а выбрасывает их код;
записи пишутся в коллекцию Qdrant `glossary` с dense- и sparse-векторами. Пересборка идемпотентна:
id записи детерминирован, исчезнувшие записи удаляются.

## Мок сервиса карточек и MCP-сервер (этап 5)

```
uv run python -m mocks.card_service --corpus data/<архив>   # мок сервиса карточек, порт 8010
uv run python -m mcp_server                                 # MCP-сервер (streamable-http), http://127.0.0.1:8020/mcp
```

- Мок реализует маршруты и pydantic-схемы реального сервиса карточек заказчика (`robot_skills`
  по `CARD_SERVICE_PATH`) и отдаёт карточки из архива экспорта. Переключение мок ↔ реальный сервис —
  только `CARD_SERVICE_URL` (и учётка `CARD_SERVICE_USERNAME`/`CARD_SERVICE_PASSWORD`).
- MCP-сервер даёт агенту пять инструментов: `hybrid_search` (dense + sparse → RRF → reranker на CPU),
  `get_document_card`, `get_related_documents`, `get_document_content`, `glossary_lookup` (термин ищется
  в коллекции `glossary` точным совпадением, затем векторами с проверкой похожести термина: сокращение
  требует точного совпадения — «ЛПУМГ» не получит определение «МГ», — у слова допускается другое
  окончание, у словосочетания — вхождение; записи действующих документов первыми). Веса bge-m3 и
  reranker'а читаются из `models/`, работа офлайн.
- В Docker те же сервисы — `mcp-server` (профиль `runtime`) и `mock-card-service` (профиль `mock`,
  `stack.py up runtime` включает его по умолчанию, `--no-mock` — для стенда с реальным сервисом).
  Образ — `docker/Dockerfile.app`; внешний код монтируется томами из `TESSA_SDK_PATH` и
  `CARD_SERVICE_PATH`, архив — из `CORPUS_DIR`, адрес сервиса карточек для контейнера —
  `CARD_SERVICE_URL_DOCKER` (по умолчанию мок).

## Агент (этап 6)

```
uv run python -m agent "Какие инструкции по охране труда утверждены приказами?"   # один вопрос
uv run python -m agent                                                            # диалог построчно
```

Нужны профиль `runtime` (vLLM с Qwen3-8B, MCP-сервер, мок карточек). Агент — LlamaIndex `FunctionAgent`
с инструментами MCP: вопрос переписывается с учётом истории диалога в самодостаточный запрос (FR-6),
цикл «поиск → проверка статуса → дочитывание → связи» ведёт LLM без режима размышлений (бюджет
8 вызовов, FR-1), итоговый ответ с самопроверкой пишет LLM с размышлениями (N9); ссылки в ответе
нумеруются и резолвятся в чанки индекса или карточки, блок «Источники» строится автоматически (FR-4).
Уточнение по уже найденному документу отвечается из кэша сессии без нового поиска; старые ходы
диалога сжимаются в сводку. В консоли видны шаги агента, заметки после поиска, готовый ответ и время.
Без поиска обрабатываются только приветствие, вопрос о возможностях и просьба переформулировать
прошлый ответ (намерение из закрытого списка на шаге переписывания); если цикл инструментов закончил
без единого поиска, раннер ищет сам по запросу и по вопросу и запускает цикл ещё раз с результатами.
В промпт ответа прочитанные разделы подаются первыми, контекст раздела — один раз, фрагменты прошлых
ходов — последними; не влезающий в бюджет фрагмент обрезается, а не выбрасывается. Аргументы
инструментов нормализуются до вызова: лишние по схеме отбрасываются, русские статусы в фильтре
поиска переводятся в коды индекса, чтобы почти верный вызов не стоил бюджета.
Заметки цикла попадают в промпт ответа только как ориентир из фактов с псевдонимами фрагментов
(предложения без псевдонима и начинающиеся с «таким образом», «значит» отбрасываются), а черновик ответа
проверяется по свидетельствам отдельным вызовом LLM с размышлениями (роль `verify`, `agent.verify` в
конфиге): предложение с числом, временем, датой, названием или правилом должно быть в тексте фрагмента по
ссылке или получено явно показанным расчётом; проверяющий только называет неподтверждённые предложения, а
вычёркивает их из черновика код (предложения с верным расчётом от времени из вопроса «12:45 + 45 мин =
13:30» защищены); если замечания отклонили весь черновик, ответ составляется заново с этими замечаниями в
промпте (`agent.verify.retry_answer`); при сбое проверки пользователь получает черновик. Пустой текст
ответа (размышления исчерпали лимит токенов) шаг ответа повторяет (`agent.answer.empty_retries`).
Аббревиатуры вопроса расшифровываются по глоссарию до поиска (FR-5): термины называет шаг переписывания,
прописные сокращения дополнительно находит regexp, расшифровка добавляется к поисковому запросу
(«…ПВТР… (ПВТР — правила внутреннего трудового распорядка)»); глоссарий читается мимо бюджета вызовов
инструментов, шаг виден в консоли, в UI и в трейсе.

- Трейсинг в Langfuse (FR-8): `LANGFUSE_ENABLED=true` и ключи в `.env` при поднятом профиле
  `observability`; каждый вопрос — трейс с шагами переписывание → цикл инструментов (LLM-вызовы и
  инструменты) → ответ, `trace_id` печатается в консоли; просмотр — http://localhost:3000.
- Живые сценарии агента (AC-1.1, AC-1.2, AC-2.1, AC-6.1) на стенде: `uv run pytest -m scenario`
  (~10 минут; из обычного прогона исключены).

## UI (этап 7)

```
uv run python -m ui                       # Chainlit на http://localhost:8080 (ui.host / ui.port из app.yaml)
uv run python -m ui --headless --migrate  # так запускается контейнер agent-ui: миграции + сервер
```

В Docker UI поднимается вместе с профилем `runtime` (`stack.py up runtime`) как сервис `agent-ui`,
порт `UI_PORT` (8080). Вход в dev — один пользователь `UI_USERNAME`/`UI_PASSWORD` из `.env`; для боевого
контура задаются переменные `OAUTH_GENERIC_*` (OIDC-провайдер заказчика), и Chainlit показывает кнопку
входа через него. Секрет сессий — `CHAINLIT_AUTH_SECRET` (`uv run chainlit create-secret`).

- Диалоги, шаги агента, элементы и оценки хранятся в PostgreSQL проекта (таблицы `conversation`,
  `message`, `element`, `feedback`) через собственный data layer Chainlit на SQLAlchemy ORM (FR-9);
  список прошлых диалогов — в левой панели, открытие старого диалога восстанавливает память
  агента и кэш найденных документов.
- Ход работы агента виден шагами в реальном времени: «Разбираю вопрос» появляется сразу после
  отправки, далее «Расшифровываю по глоссарию: …» (если в вопросе есть известная аббревиатура),
  «Ищу: «…» → Найдено фрагментов: N», «Читаю карточку…», «Итоги поиска» (FR-7); после
  стрима — «Проверяю ответ по фрагментам → Проверка ответа: замечаний нет» либо «вычеркнуто
  неподтверждённое, замечаний — N» со списком замечаний и решением по каждому, и готовое сообщение получает
  текст без вычеркнутых предложений; если отклонён весь черновик — шаг «Черновик не подтверждён
  свидетельствами, составляю ответ заново», стрим начинается заново и проверяется ещё раз.
- Ответ стримится; ссылки [1], [2] в готовом ответе кликабельны и открывают сбоку текст именно того
  фрагмента или карточки, на которые ссылается утверждение; блок «Источники» — в конце ответа (FR-4).
  Панель «Список источников» Chainlit открывает сам после ответа.
- Если после перезапуска стенда vLLM ещё грузит модель, вопрос не падает ошибкой: UI показывает шаг
  «Модель ещё загружается, жду готовности» и ждёт до `ui.llm_ready_wait_s`, затем отвечает.
- 👍/👎 под ответом пишутся в `feedback` с `trace_id` ответа и уходят score `user_feedback` в трейс
  Langfuse; логики поверх оценок нет (§7 ТЗ).
- Настройки Chainlit — `.chainlit/config.toml`, русский интерфейс — `.chainlit/translations/ru-RU.json`,
  справка в приложении — `chainlit.md`.

### Почему Chainlit

ТЗ (§3) допускает Chainlit, Gradio или Streamlit; выбор Chainlit подтверждён заказчиком 2026-09-14.
Причины: из трёх вариантов только Chainlit из коробки даёт всё, что требуют FR-4, FR-7 и FR-9 —
пошаговое отображение работы агента (`cl.Step`) параллельно со стримом ответа, кликабельные источники
рядом с сообщением, встроенные 👍/👎 и подключаемый data layer, в который лёг наш PostgreSQL на
SQLAlchemy ORM (история диалогов — наша схема, не чужая БД). Аутентификация тоже встроена: в dev —
пароль одного пользователя, в контуре заказчика — OIDC через `OAUTH_GENERIC_*`, без изменения кода.
Gradio и Streamlit потребовали бы писать шаги, цитаты, историю и вход самостоятельно. Цена выбора —
привязка к формату Chainlit: своя вёрстка ограничена его компонентами.

## Оценка качества (этап 9)

```
uv run python -m eval.run                                  # весь голден-сет, отчёт в eval/reports/
uv run python -m eval.run --only simple no_answer --limit 5  # часть сета (категории или id вопросов)
uv run python -m eval.run --no-judge                       # только детерминированные проверки
```

Голден-сет (§10.1) — YAML с полями `id, category, question, expected_answer, expected_doc_ids, notes`
(плюс `follow_up`/`follow_up_expected` для двухходовых сценариев и `derived` для вопросов на расчёт);
формат и правила — `src/eval/golden_set.py`, образец — `eval/golden_set.example.yaml`. Сет по реальному
корпусу лежит по пути из `eval.golden_set` и в git не коммитится: он состоит из вопросов, эталонов и ID
документов заказчика.

Каждый вопрос идёт в агента отдельной сессией (уточнение сценария `clarification` — в той же сессии).
По ответу считаются детерминированные признаки: ожидаемые документы в источниках (M1), потерянные
ссылки (M3), явный отказ (M4), статусы процитированных документов (M5); корректность, покрытие ссылками
и поддержку ссылок фрагментами оценивает LLM-судья на той же Qwen3-8B отдельным промптом с температурой 0
(`eval.judge`). Вопрос, по которому судья не ответил, в судейские метрики не идёт и виден в отчёте
отдельно. Отчёт пишется парой файлов (markdown и json) в `eval.reports_dir`, json прошлого прогона даёт
diff по метрикам и по каждому вопросу. M8 берётся из отчёта инжеста.

### Как снять метрики M1–M8

1. Поднять профиль `runtime` и убедиться, что индекс собран по реальному корпусу
   (`scripts/run_ingest.py run --corpus …`): на синтетике метрики не считаются, отчёт помечает это.
2. Положить голден-сет по пути из `eval.golden_set` (в git его нет — см. выше).
3. `uv run python -m eval.run --tag <метка>` — полный прогон, 28–35 минут на 59 вопросов.
4. Отчёт — `eval/reports/<метка>.md` (таблица метрик, разбор по вопросам, diff с прошлым прогоном).

Одна и та же конфигурация даёт разброс ±10–15 п.п. в категориях по 6–10 вопросов: один вопрос стоит
10–17 п.п. Поэтому значение метрики принимается по медиане трёх прогонов, а не по лучшему.
Последний замер и что в нём не достигнуто — `docs/metrics_report.md`.

## Синтетический корпус

```
uv run python scripts/make_synthetic_corpus.py   # data/corpus/: 13 карточек, 28 файлов, отчёт валидации
```

Формат — тот же, что у реального экспорта (`export/cards`, `cards_raw`, `files`, `manifest.json`,
`links_graph.json`, `validation_report.md`); карточки валидны по схеме `CardData` сервиса карточек.
Каталог с реальным экспортом скрипт не перезаписывает.

## Внешний код

Код SDK Тессы и FastAPI-сервиса карточек заказчика в репозиторий не копируется (§8.0 ТЗ).
Пути задаются в `.env` (`TESSA_SDK_PATH`, `CARD_SERVICE_PATH`); pydantic-схемы карточек
импортируются как внешний пакет через `src/contracts/`. Без путей зависящие от них тесты скипаются.

Экспорт-скрипт для контура заказчика: `tools/tessa_export/README.md`.
